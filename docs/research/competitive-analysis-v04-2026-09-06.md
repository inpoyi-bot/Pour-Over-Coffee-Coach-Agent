# 咖啡 Agent 竞争研究 v04：定位与商业化验证的调整、并行工作包

> 日期：2026-09-06，Asia/Singapore。
> 前版：[v03 统一走查协议](competitive-analysis-v03-2026-09-06.md)、[v02 功能拆分与路线建议](competitive-analysis-v02-2026-09-06.md)。保留旧版。
> 本版用途：调整“竞争定位与商业化路径验证”的依赖顺序，定义在用户走查时可以推进的独立工作。
> 状态：方案与工作包定义已完成；竞品走查、以下工作包的新研究、访谈及商业试点均未完成。本版不改变 feature freeze，不创建或启动其他 Codex 任务。

## 1. 推荐调整

**保留新豆调校作为首选验证场景，将下一阶段组织成“产品行为 + 用户问题 + 商家/市场条件”三类证据的汇合。** 走查不必成为所有工作开始的前提，也不能凭一个竞品缺陷就决定做同类功能。

目前的核心投资问题：有基本器材、但换豆调校不稳定的人，是否能从我们的帮助中获得足够收益，以至于愿意持续反馈，并由自己或商家承担成本？

| 原方案的风险 | 本版调整 | 原因 |
| --- | --- | --- |
| 走查后直接提功能改进 | 将每个缺口与真实用户问题交叉验证 | 不好用的功能可能根本不重要，缺少的功能也不一定有人需要 |
| “跨杯记忆 + 收敛”被当作定位 | 用目标人群、触发场景、结果与替代方案定义定位 | 技术机制存在竞争，用户购买的是改善和便利 |
| 两周内同时验证体验、效果、留存、支付 | 两周作为第一轮证据检查点；真实复现、换袋续用、支付各保留观察周期 | 模拟走查不验证味道，一包豆也不验证跨袋留存 |
| B2C 与 B2B2C 同时铺完整产品 | 共用消费者价值验证，分别验证付款人的经济理由 | 使用者与付款人不同，但商家付费不能代替消费者受益 |
| 全球扫描容易无止境 | 保留六产品基线，新增竞品需回答新的竞争问题 | 优先补反例、市场和反馈，而非增加品牌数量 |
| 看到缺口就改原型 | 在研究汇合后选一个最小验证流程 | 当前提交范围冻结；商业化研究不等于获准扩功能 |

## 2. 调整后的定位假设

优先顺序按现有能力与证据缺口提出，尚未锁定产品方向。

| 优先级 | 定位假设 | 用户/触发 | 相对替代方案的候选收益 | 主要反证 |
| --- | --- | --- | --- | --- |
| 首选验证 | 新豆调校帮助 | 有 V60、可调磨豆机和基本手法，换豆后仍靠猜 | 下一步更明确，较少无效尝试，满意配方可复用 | 固定配方已足够；用户不愿持续反馈；效果不稳定 |
| 条件成立再推进 | 烘焙商提供的冲煮售后帮助 | 买豆后按指南仍冲不好的客户；商家负责支持 | 客户问题更易解决，商家支持投入有望降低 | 求助很少；指南已解决；人工服务本身是品牌价值；没有预算 |
| 保留为转向选项 | 低负担记录与复现 | 想记住好喝参数、但不需要诊断的人 | 方便找回满意杯和下一袋起点 | 免费记录工具已经足够，切换和付费理由弱 |

初步价值主张：**每次换豆时，帮你找到容易执行的下一步，保留下次愿意照做的配方。** 不先宣称节省几杯、提升多少风味或比竞品更可靠，这些需要证据。

定位最终应包含：谁 → 什么时刻 → 遇到什么问题 → 今天怎么解决 → 我们改善什么 → 用户为什么相信。产品名称、界面风格和收费套餐不先于这些问题。

## 3. 五条假设与证据要求

| 假设 | 本轮能获得的证据 | 后续必须补的证据 | 不能替代它的指标 |
| --- | --- | --- | --- |
| H1 调校问题反复发生 | 公开第一人称经历、实际问题及替代行为 | 目标用户近期经历与出现频率 | 咖啡市场大、论坛帖子多 |
| H2 用户能低负担完成反馈 | PM 走查的字段、时间、表达限制 | 真实用户独立完成及自然继续使用 | 我们自己觉得简单 |
| H3 建议有增量价值 | 输入、历史与输出的可见一致性 | 真实冲煮改善、满意配方后续复现，合理对照 | 输出听起来专业、功能更多 |
| H4 有人愿意承担成本 | 竞品价格/免费边界、商家问题线索 | 实际报价后的支付，或有资源/预算的试点承诺 | 评分、免费试用、口头喜欢 |
| H5 能以合理成本交付 | 原型差距、成本项目与计量方案 | 实际模型调用、人工支持、获客与履约成本 | 只计算一次模型调用费用 |

## 4. 可以同步推进哪些工作

建议控制同时推进的工作量：用户主线为 A；研究侧先推进 B，再按容量推进 C。D 的代码阅读部分和 E 的模型结构可以准备，但依赖项不得猜填。以下是可分派的工作包，不是已运行任务。

| 工作包 | 优先级 | 负责人建议 | 是否等走查 | 具体交付 |
| --- | --- | --- | --- | --- |
| A 竞品实机走查 | 当前主线 | 用户操作；Codex 分析 | 不等，执行 v03 | Cupsight / Pourist 的任务证据与差异 |
| B 用户痛点与替代行为 | P0，先做 | Codex 公开资料研究；PM 审核解释 | 不等 | 用户证据表、痛点/反例、待访谈问题 |
| C 烘焙商服务与渠道 | P0，第二个 | Codex 公开资料研究；用户后续访谈 | 不等 | 商家案例、现有指南/求助路径、潜在试点条件 |
| D 原型进入用户试点的差距 | P1 | Codex 只读检查；PM 定取舍 | 可先检查；最终方案等 A/B | 必要交付缺口、人工替代方式、能力声明边界 |
| E 收费与成本假设 | P1 | Codex 整理；PM 决定报价测试 | 可列结构；具体报价等 B/C | 收费单位比较、成本项、待测变量 |
| F 真实用户试点 | 汇合后 | PM/用户招募执行；Codex 分析 | 等 A/B/D；商家版还等 C | 使用行为、实际冲煮、复现和支付证据 |

### B｜用户痛点与替代行为证据

**要回答：** 用户真正卡在获取配方、执行动作、表达味道、决定下一步，还是记录复现？现在靠什么解决，为什么继续/放弃？

建议执行范围：先整理 5 条不同类型的样本检验编码，再扩到约 20–30 条去重的第一人称经历。数量是研究预算，不是代表性样本。优先近 12 个月；更早案例因相关性纳入时标日期。不要仅搜抱怨，还要找“现有方法足够”和“不想用 App”的反例。

来源优先：App 商店文字评论、用户原帖和后续回复。开发者推广、媒体测评、官方案例另分类，不能计入独立消费者经历；品牌名不是唯一搜索入口，也查“新豆如何调”“不想记参数”等任务语言。

每条记录：链接/发布日期/检索日期/语言；自述经验及器材（未提就未知）；触发情境；问题；已尝试方案；实际付出的时间/耗豆/求助（仅按原文）；结果；切换/放弃行为；来源偏差；对应 H1–H4。

交付标准：

- 形成 3–5 个候选问题主题，每个都链接具体证据，单一来源的主张保持为线索。
- 保留正面、负面和不需要产品的样本；无反例时写明未找到，不能制造反例。
- 合并转载、重复评论及同一人的同一事件；报告条数和独立来源，不把帖子占比当市场发生率。
- 将“AI 教练是否必要”拆开：用户是否只需要计时、配方起点或查阅旧记录。

**与走查的连接：** A 找到的每个重要断点，都查 B 是否有相应用户任务证据；B 出现的强问题若 A 未覆盖，作为后续场景候选，不在两款测试中途静默改协议。

### C｜烘焙商服务与渠道研究

**要回答：** 商家今天如何帮助客户把豆冲好？已有配方卡、QR、视频或人工支持能否解决？后续调校服务可能进入哪个触点？

建议先取 4 个不同服务形态的公开案例，再扩到约 8–12 家，覆盖不同地区和规模。抽样依据为服务形态与可观察性；不凭粉丝量或目录收录认定它愿意合作。研究市场数据时逐条注明地区、年份和口径。

观察字段：商品页信息、按豆配方/通用指南、设备设置、扫码/邮件/聊天入口、购后指引、订阅豆服务、求助与复购路径、可核验客户反馈、已有技术集成及证据日期。

交付标准：

- 比较“有通用指南”“有逐豆指南”“有人工调校支持”等服务形态及可见缺口。
- 列出少量可能有访谈价值的候选及理由，同时写明什么信息会排除它。
- 区分公开渠道存在、可能痛点、已确认痛点、预算与合作承诺；后四者不得靠网站推断升级。
- 访谈再核查每百笔订单求助量、处理分钟数、问题解决情况、预算人；无数据就未知。

**与走查的连接：** C 可以独立检查获客/服务触点，具体产品演示和试点承诺需要 A/B/D 支持。不能从 BaseBrew 的营销数字推导商家 ROI。

### D｜原型进入试点的差距

只读检查已有流程：新用户能否进入、能否记一包豆、是否保留实际反馈、满意配方如何返回、错误如何恢复、人工介入在哪里。按“试点必需 / 可暂由人完成 / 后置”分组；每条关联代码或当前文件。

保留 E11/E13 限制，不把已有测试名字等同于稳定能力。现有 demo 前端与 FRONTEND 草稿也需区分。先形成一个最小试点路径；任何改代码、解冻参数或新增 eval 的决定单独讨论。

如果研究者人工补救，记录时间、动作与费用。人工辅助的服务结果与无干预 Agent 表现分别报告。

### E｜收费单位与成本结构

先比较按包/单次、消费者订阅、商家付费各自覆盖的任务和使用频次，不现在给最终价格。竞品商店价作为供给侧参照，免费边界和本地币种同时记录。

成本结构至少包含：模型使用、数据/托管、支付退款、人工支持、商家接入与维护、获客。没有测量就留作变量；按包收入不能直接与按月成本比较。之后用试点真实使用频率和人工量补参数，避免只看模型费用判断可盈利。

## 5. 工作依赖与汇合方式

| 当前独立输入 | 汇合检查 | 后续动作 |
| --- | --- | --- |
| A：竞品可见行为 + B：用户问题与替代行为 | 缺口对应反复出现且未被现有方法充分解决的问题吗？ | 保留最多两个候选机会 |
| 候选机会 + D：我方能力/流程边界 | 哪一个能以当前能力进行可信试点？ | 定义一条最小体验，不先建完整商业 App |
| C：商家服务/市场条件 + E：成本结构 | 谁得益、谁付款，是否具备现实分发条件？ | 选择 B2C 或商家试点的优先路径 |
| 使用者、最小体验、付款假设 | 真实使用/复现及报价测试 | 继续、修改或暂停下一笔投入 |

首个汇合点建议为：两款主流程走查已有证据、用户问题出现初步主题。异常分支尚未全部完成不必阻止汇合，但依赖 B1–B3 的能力结论继续留空。

遇到走查无法进入、付费墙或基线无法复刻时，A 如实记录；B/C/D 可继续。不要让一个 App 的访问限制阻塞整项商业研究。

## 6. 如何调整原来的“两周计划”

将两周保留为第一轮研究节奏，不承诺两周内完成商业化验证。

1. **现在：**用户执行 v03 的主流程；研究侧先 B，随后 C；D/E 只做可独立准备的部分。
2. **首轮汇合：**选出一个目标场景和一到两个关键假设，同时列反例。暂不锁定首发国家；测试所在地与首发市场分开。
3. **具备招募与环境后：**做 6–8 位目标用户的探索性试点，观察实际行为。数量用于发现问题，不用于市场比例推断。
4. **跨过一包豆之后：**再看下一袋是否继续用；B2B2C 的复购/支持效果按商家实际周期评估，不能压缩为几天。
5. **真实报价之后：**结合实际支付或商家资源承诺、交付成本决定下一步。没有支付不等于产品毫无价值，但不能宣称商业模式成立。

候选首发地区的筛选可在 C 中形成资料清单：目标人群可触达性、设备与语言覆盖、支付/分发条件、愿意参与的渠道资源、服务成本。当前缺少可比证据，不给国家排名或 TAM 点估计。

## 8. 分工与决策归属

- **用户/PM：**实机操作、研究方向取舍、目标人群、体验优先级、测试验收与功能范围、是否招募/联系商家以及最终付款/上线决定。
- **Codex：**公开研究、证据去重与编码、录屏分析、本地只读差距检查、成本结构、迭代 MD 与建议。
- **需要真人参与的后续工作：**真实冲煮、用户访谈、商家信息核查；公开网页不能替代。

工作包可以在不同任务中执行，但创建单独任务、执行研究、外部联系是不同动作。本版只定义计划；没有启动后台持续工作、自动化或其他任务，也未联系任何人。
